# Verification: proving "exactly like before"

This is the load-bearing part of shrinkcode. Compression without verification is
just "I made it shorter and I hope it still works" — not acceptable. Verification
rigor scales with the risk tier of the change (see `risk-classification.md`) — a
Tier 1 mechanical deletion needs less ceremony than a Tier 3 async-ordering change,
but every tier requires *something real*, never just "I read the diff and it looks
fine."

## Step 0: Metrics baseline, not just tests

Before any edits, capture all three shrinkcode metrics, not just "does it still
work":

```bash
python3 scripts/loc_report.py <path> --save before_loc.json
python3 scripts/complexity_report.py <path> --save before_complexity.json
bash scripts/dead_code_scan.sh <path> > before_deadcode.txt
```

This matters because "exactly like before" and "actually smaller/simpler" are two
separate claims — the metrics baseline is how you prove the second one at the end,
not just the first.

## Step 1: Behavior baseline, before any edits

**If tests already exist:**
- Run the full suite, record pass/fail counts and timing.
- Check coverage if a coverage tool is available. Any code path you're about to
  touch that has zero coverage needs a characterization test added before you
  compress it (see below) — otherwise you have no way to know you preserved it.

**If no tests exist (common in vibe-coded / prototype projects):**
- Do not skip verification just because there's no test suite. Instead, write a
  small set of **characterization tests**: tests that just pin down current
  behavior (call the function/endpoint/component with representative + edge-case
  inputs, record the exact output), not tests of what behavior *should* be. You're
  not doing TDD here, you're building a tripwire.
- Prioritize: main happy-path flows, then the weirdest/gnarliest edge cases you
  can find in the code (error handling branches, boundary values, empty/null
  inputs, concurrency-sensitive bits) — and specifically the exact edge case any
  planned Tier 3 change could affect (see risk-classification.md: a planned
  `Promise.all` conversion needs a characterization test for the rejection path,
  not just the happy path).
- For a CLI tool or script: capture stdout/stderr/exit code for a handful of
  representative invocations.
- For an API/backend: capture request → response pairs for the main endpoints,
  including error responses (4xx/5xx paths) and exact status codes/shapes.

### Finding the gaps with `coverage_gap_scaffold.py`

Locating the zero-coverage paths by hand doesn't scale, so let the bundled
scaffolder scope them and stub the tests:

```bash
python3 scripts/coverage_gap_scaffold.py src/thing.py src/other.js
```

It runs the project's coverage command (Python: `coverage run -m pytest` +
`coverage json`; JS/TS: vitest/jest with the lcov reporter — set
`coverageCommand` in `shrinkcode.config.json` so it doesn't have to guess), then
writes one stub file per target next to it: `test_characterization_<module>.py`
or `<module>.characterization.test.js`. One test per uncovered function, with
placeholder arguments inferred from the signature (`email` → a placeholder
email, `isAdmin` → `true`, unmatched names → `None`/`null`) and a
`TODO(shrinkcode)` marker **instead of an assertion**.

The loop it's built around:

1. Run the generated tests. Each prints `ACTUAL: <value>` or the exception it
   raised — that's the real current behavior. Never invent the expected value:
   a fabricated assertion silently encodes a guess as "current behavior".
2. Replace the commented-out lines with what you actually saw.
3. Re-run the scaffolder. What you pinned is now a real tripwire, and the stub
   set only ever shrinks from here — functions that gained real tests drop out,
   and a stub with nothing left to pin is removed.

Two details that are what stop it from destroying your work:

- Stubs it generated but you haven't pinned yet are held out of the coverage
  run (`--ignore` for pytest; for JS the file is renamed to `*.pending` around
  the runner and restored right after). Without that, the stub's own
  placeholder call would make its target look covered and the tool would delete
  the very TODO you still have to fill in.
- A stub containing an `assert`/`expect(` is never rewritten or deleted, and a
  file that wasn't generated by shrinkcode is left alone entirely.

The generated file is valid and runnable as written — it passes, it just
asserts nothing yet. Class members (`ClassName.method`) and nested functions
get a `print`/`console.log` `SKIPPED` line with instructions instead of a call,
since a test can't reach them without a hand-built receiver; they're still
listed so the gap stays visible. For anything beyond function-level gaps
(React rendered output, HTTP request/response pairs, CLI stdout/exit codes)
write the baseline by hand as described above — the scaffolder only automates
the mechanical part.

## Step 2: Verify after every batch, at the bar its tier requires

| Tier | Minimum verification bar |
|------|---------------------------|
| 1 (mechanical) | Full test suite once per batch |
| 2 (structural) | Full test suite + relevant characterization tests, per individual change (not batched) + UI visual/interaction check if applicable |
| 3 (semantic) | Everything in Tier 2, plus a characterization test for the specific edge case the semantic change affects, plus explicit user sign-off before applying |

On any failure: stop, isolate which specific change caused it (this is exactly
why batches are committed individually — see `git-workflow.md`), fix or revert
that change specifically. Don't keep compressing on top of a broken baseline.

## Stack-specific notes

### Python
- `pytest` if a suite exists; otherwise a quick `unittest`/`pytest` file with
  characterization tests is enough scaffolding — it doesn't need to be permanent.
- Watch for behavior hiding in exceptions: a bare `except:` that silently
  swallows errors is itself part of "current behavior" until the user says
  otherwise. Don't silently fix that while compressing — that's a behavior
  change, flag it separately (see `python.md`).

### TypeScript / JavaScript (Node or browser logic)
- `vitest`/`jest` if present. For browser-only logic with no test runner set
  up, a minimal `vitest` config is fast to add temporarily.
- Async ordering matters: compressing multiple sequential awaits into
  `Promise.all` is a Tier 3 **behavior change** if the original relied on
  ordering or early-exit on the first rejection — verify this explicitly with
  a rejection-path characterization test, don't assume parallelizing is safe.

### React / Next.js
- Behavior baseline here includes **rendered output and interaction**, not
  just function return values. At minimum:
  - Snapshot (or manually diff) the rendered DOM/markup for each affected
    component/page before and after, for its main prop/state variations.
  - Click through / trigger the main interactive flows (form submit, route
    navigation, conditional rendering toggles) before and after.
  - If React Testing Library / Playwright / Cypress is already in the
    project, use it. If not, and the job is small, manual before/after
    screenshots + interaction walkthrough is an acceptable minimum bar — but
    say so explicitly in your report rather than silently skipping automated
    checks.
- Watch for: merging components changing when effects run (`useEffect`
  dependency arrays), or hooks reordering (React requires stable hook call
  order — a "cleanup" that moves a hook behind a conditional is a real bug,
  not just a style nit). See `react-nextjs.md`'s hard correctness rules.

### Vue / Svelte
- Same principle as React: rendered output + interaction, not just logic
  return values. See `vue-svelte.md` for the reactivity-tracking pitfalls
  specific to each (`watch`/`watchEffect` in Vue, `$:` dependency inference in
  Svelte) that make certain refactors Tier 2/3 rather than Tier 1.

### HTML / CSS
- Visual output is the behavior here. Before/after screenshot comparison (or
  at minimum a careful manual visual diff) across the breakpoints/states the
  original supported (mobile/desktop, hover/focus states, dark mode if
  present).
- Collapsing CSS (merging selectors, replacing repeated declarations with a
  utility class or CSS variable) can change specificity/cascade order —
  verify computed styles didn't shift, not just that the file looks
  equivalent.

### Node.js backend
- API contract is the behavior here, not just "the function returns the
  right value in isolation." Capture request → response pairs (status code +
  body shape) per route, including error paths, before touching middleware or
  shared error-handling logic. See `nodejs-backend.md` for the specific
  pitfalls (middleware ordering, transaction boundaries).

## What "verified" means in your final report

Never write "this now functions identically" unless you can point to what you
actually ran to check that, at the bar its risk tier required. If verification
was partial (e.g. you only manually smoke-tested 3 of 10 endpoints, or skipped
the Tier 2 bar on something that turned out low-risk on inspection), say
exactly that — partial verification honestly reported is far more useful to
the user than a confident claim you can't back up. Pair this with the metrics
diff (`loc_report.py --diff`, `complexity_report.py --diff`) so "verified and
smaller/simpler" is a claim backed by two independent kinds of evidence, not
one.
